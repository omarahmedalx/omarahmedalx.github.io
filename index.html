📊 Exploit Execution

🎯 Attack Flow

  1. Victim visits attacker's website (omarahmedalx.github.io) while logged into drive2.ru
  2. Malicious JavaScript executes in the victim's browser context
  3. Cross-origin request is sent to upload.drive2.ru/_api/upload with victim's cookies
  4. Server accepts the request because CORS headers are misconfigured (Access-Control-Allow-Origin: * or origin reflection)
  5. File is uploaded to victim's account with victim's authentication tokens
  6. Response leaks file metadata including upload ID and publicly accessible URLs
  7. Attacker can distribute malicious content using victim's account and drive2.ru's trusted domain

💡 How It Works

The vulnerability exists because the server at upload.drive2.ru is configured to:

  1. Reflect the Origin header: Instead of maintaining a whitelist, the server mirrors back whatever origin sent the request
  2. Enable credential sharing: Access-Control-Allow-Credentials: true allows cookies/tokens to be sent cross-origin
  3. Skip CSRF protection: No token validation means any site can trigger uploads on behalf of authenticated users
  4. Accept cross-origin file uploads: No additional validation prevents unauthorized multipart requests

🔐 Remediation

  1. Whitelist Origins: Define specific allowed origins instead of using wildcards or reflection
  2. Remove Unnecessary Credentials: Only enable Access-Control-Allow-Credentials when absolutely required
  3. Implement CSRF Tokens: Require server-generated tokens for state-changing operations
  4. Validate File Uploads: Verify MIME types, file size, and content server-side
  5. Use SameSite Cookies: Set SameSite=Strict or SameSite=Lax on authentication cookies

📝 Responsible Disclosure: Report vulnerabilities to the vendor's security team with a reasonable disclosure timeline (typically 90 days) before public disclosure.
